This app connects to an STM32 Black Pill running the silkscreen firmware over USB.

To connect:

  1. Plug the board into a USB port.
  2. It should appear in the port dropdown above, marked "(STM32)" when detected automatically.
  3. Click Connect.

Once connected, use Configuration to view and change device settings, Telemetry to watch live sensor data, and Terminal for direct command-line access to the device for debugging. Some pages will be greyed out until a device is connected.

Need help? See the Help page for troubleshooting tips.

Getting into DFU mode by hand

Needed for the very first flash, and any time the firmware on the board is broken:

  1. Hold the BOOT0 button down.
  2. Tap NRST and release it.
  3. Release BOOT0.

The board then disappears from the port dropdown and shows up as a DFU device instead — the badge at the top of this page turns amber. This page keeps working while disconnected, which is the whole point: a board that needs re-flashing often can't be talked to.

Advanced: flash a local file
Nothing verifies this file matches your board. A bundled image above is checksummed against the manifest; a file you pick is only sanity-checked for being a raw firmware binary at all. Flashing the wrong one leaves the board unbootable until you re-flash it (BOOT0 + NRST still works, so this is recoverable — just tedious).

For a locally built image this is firmware/.pio/build/<env>/firmware.bin — the .bin, not the .elf or .hex beside it.

The board doesn't appear in the port dropdown

  • Check the USB cable is a data cable, not a charge-only cable.
  • Make sure the board is powered — you should see LED activity on it.
  • Try unplugging and replugging the cable, then check the dropdown again.

Connect fails or times out

  • Confirm you selected the right port — a detected STM32 board is marked "(STM32)" in the dropdown.
  • Make sure no other program (a serial monitor, another instance of this app) already has the port open.
  • Try disconnecting and reconnecting.

Connected, but no telemetry appears

  • Check the Telemetry Rate setting on the Configuration page isn't set very low.
  • Try disconnecting and reconnecting.

Changing a setting doesn't seem to do anything

  • Changes apply to the device immediately, but only persist through a power cycle after you click Save.
  • An invalid value (out of range, too long) is rejected and shown with a red outline — check for that.

The status badge shows "stale"

  • This means the device is still connected but hasn't sent telemetry recently — often just a brief pause during a Save (writing to flash takes about a second). If it doesn't clear on its own, try disconnecting and reconnecting.

Backing up and restoring settings

  • On the Terminal page, type dump to print every setting as INI text, then copy it into a file. list shows what each setting accepts.
  • Restore from INI… reads such a file back. Settings the connected firmware doesn't have — or values it rejects — are listed as skipped and the rest still apply.
  • A restore applies to the device immediately but is not written to flash. Click Save to flash — the button beside Restore, or the one on the Configuration page — to keep it. It stays greyed out until there is something unsaved.

Undoing changes you haven't saved

  • Discard changes reloads the settings last written to flash, so it undoes everything since your last Save. This is different from Load defaults, which goes to the firmware's factory values — somewhere you may never have saved.
  • On a board that has never been saved to, there is nothing stored to go back to, so Discard changes loads the defaults instead and tells you it did.

A saved setting didn't survive a restart

  • Confirm you clicked Save after changing the value, not just changed the field — edits apply live but aren't written to flash until Save.

Updating the firmware

  • The Firmware page flashes the images this app shipped with, so the firmware and the app always match.
  • The board has to be in DFU mode first. If it's running and connected, Reboot to DFU does it for you. Otherwise: hold BOOT0, tap NRST, release BOOT0.
  • The button is greyed out on firmware built without DFU support — use the BOOT0 method for those.

The board doesn't show up as a DFU device

  • Check the badge at the top of the Firmware page. If it says "no DFU device" after the BOOT0 sequence, the sequence didn't take — the order matters: BOOT0 held down first, then NRST tapped, then BOOT0 released.
  • A board in DFU mode disappears from the port dropdown. Seeing it in both places at once means it never left normal mode.

The flash failed partway through

  • The board is half-written, not bricked. Put it back into DFU mode with BOOT0 + NRST and flash again — the whole image is rewritten each time.
  • If the board no longer enumerates as anything at all, BOOT0 + NRST still reaches the ROM bootloader; it lives in read-only memory and cannot be erased.

It flashed, but the board stayed in DFU mode

  • Tap NRST. The flasher asks the bootloader to restart into the new firmware when it finishes, and that request is occasionally ignored.
